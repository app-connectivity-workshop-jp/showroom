== Module 2: {rhossm} によるマイクロサービスアクセス制御の保護
{m2}

{corp} のマイクロサービスベースのアーキテクチャへの移行は、より高い俊敏性をもたらしますが、マイクロサービスが互いに通信し、安全を保つ方法を管理する複雑さも増加させます。

{corp} は、マイクロサービス間の相互作用にアクセスポリシーを適用し、複雑なデプロイメント戦略を可能にし、マイクロサービスアプリケーションを監視したいと考えています。

=== ソリューション概要

{corp} は、サービス間認証、Canary リリースなどの複雑な運用機能、サービス間のトラフィックを理解するためのテレメトリをセットアップする簡単な方法として {rhossm} を活用します。

{rhossm} は、コア Service Mesh 実装として https://istio.io/[Istio^] を使用し、メッシュの設定、可視化、検証、トラブルシューティングを支援するために https://kiali.io/[Kiali^] を含んでいます！

image:m2/m2-arch.png[]

この Module では、*travel-agency* Namespace をメッシュにオンボードします。Service Mesh は、アプリケーションコードの変更を必要とせずに、この Namespace 内のマイクロサービスに透過的なレイヤーを追加します。

Namespace が Service Mesh の一部になると、Kiali を使用してサービストラフィックを可視化し、アプリケーションへの Observability を得ることができます。


== 技術的考慮事項

{rhossm} を正常に実装するには、いくつかの重要な技術的要因を考慮する必要があります：

* *Namespace とワークロード設定*: ワークロードが、Sidecar インジェクションが有効になっている、メッシュ参加用に設定された Namespace にデプロイされていることを確認します。

* *mTLS とアイデンティティ*: {rhossm} は、サービス間トラフィックの認証と暗号化に Mutual TLS (mTLS) を使用します。適切な証明書管理とアイデンティティポリシーが不可欠です。

* *認可ポリシー*: AuthorizationPolicy CRD を使用して、サービス間の最小権限通信を強制する細かいアクセス制御を実装できます。

* *トラフィック管理*: Canary デプロイメント、トラフィック分割、フォールトインジェクションには、VirtualServices と DestinationRules を使用した明確に定義されたルーティングルールが必要です。

* *Observability スタック*: Kiali、Distributed Tracing、Prometheus などのツールがサービスの可視化、トレーシング、メトリクスのために含まれています。これらが適切にデプロイされ、アクセス可能であることを確認してください。

これらの技術的基盤により、{corp} は本番環境で {rhossm} のメリットを完全に実現できます。


=== アクティビティ概要:

この Module では、OpenShift Service Mesh を使用したハンズオン体験ができます。

* OpenShift Service Mesh の主要部分を探索して、その仕組みを学びます。サービスが互いにどのように通信するかについての可視性と制御がどのように提供されるかを確認します。

* ゼロトラストセキュリティの原則を使用して、適切なサービスのみが機密性の高いバックエンドにアクセスできるようにし、不要なアクセスからアプリケーションを保護します。

* サービスバージョン間のトラフィックフローを制御して、変更を段階的にロールアウトし、デプロイメントリスクを軽減し、本番環境で安全に更新をテストできるようにします。
